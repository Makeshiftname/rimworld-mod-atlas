# records — Mod 分析记录标准

> 开始分析任何 mod 前先读本页。记录保存调查过程、证据、反面发现和修改建议，不等同于 mod 代码样本，也不等同于提炼后的通用知识。

## 1. 术语

| 词 | 含义 | 不要混用的近似说法 |
|---|---|---|
| **记录** | `records/<stable-id>/README.md` 这一份分析 | ≠ 改后的 mod 本身 |
| **它是什么** | 这个 mod 的功能、数值、手法——它自己的事实 | ≠ 我对它的评价 |
| **怎么验的** | 我的核验方法 + **阳性对照** + **自查纠错** | ≠ 结论本身 |
| **阳性对照** | 证明核验工具本身可信的那个已知有效样例 | 见第 5 节 |
| **自查纠错** | 本次分析里我自己的工具犯过错、被纠正的记录 | 见第 5 节 |
| **可复用结论** | 脱离本 mod 仍然成立的通用经验 | ≠ 本 mod 的专属细节 |
| **修改建议** | 待办项，可选章节，没有就删掉整节 | ≠ 已执行的改动 |
| **提炼** | 把复核过的通用结论沉淀进知识页 | 见第 6 节 |

## 2. 身份与目录

- 每份记录目录名来自 [`mods/registry.json`](../mods/registry.json) 的稳定 `id`，不再使用旧编号或“源目录名必须一致”的规则。
- 记录可以只对应分析对象，不一定在 `mods/` 中有代码样本；这类条目在注册表中是
  `code: null` + `record` 非空，不再使用 `record-only` 目录类别。
- 每份记录目录同时包含 `README.md` 与 `record.json`；`record.json` 是索引和校验读取的元数据来源。
- `package_id`、作者、授权和来源目录写进 `record.json`；正文仍可补充当时的证据细节。
- 身份冻结后不随来源目录改名而变；需要重命名时在注册表登记 `aliases`，不迁移已有记录 ID。

## 3. 记录骨架

四个必答锚点，标题固定、不加编号：

```markdown
# <mod 名称> — 分析记录

## 身份卡

## 它是什么

## 怎么验的

## 可复用结论

## 修改建议        ← 可选；没有待办就整节删掉
```

- mod 专属细节写成 `###` 三级标题，挂在对应锚点下。
- 需要额外维度（上下游、冲突面、依赖图）时，放在「怎么验的」之后。
- 身份卡至少记录：名称 / packageId / 作者 / 授权 / 规模 / 类型 / 支持版本 / 外部依赖及安装状态。
- 「它是什么」只写这个 mod 自己的事实，不把评价混进去。
- 「怎么验的」必须写可复现方法、阳性对照和自查纠错。
- 「可复用结论」写成能迁移到其他 mod 的判断规则。
- 「修改建议」只列待办；没有就删掉整节。

## 4. 核验的四档深度

按 mod 规模选择最高适用的一档：

| 档 | 触发条件 | 手法 |
|---|---|---|
| ① 极小 | 2–4 文件、纯 XML | 精读 + 交叉引用 + 贴图核实 |
| ② 中 | ~15 文件、单一机制 | 精读 + 逐文件 diff + IL 反射 |
| ③ 大 | 30+ 文件 / 150+ Def | 脚本批扫 defName、ParentName、引用字段与 texPath，再精读关键片段 |
| ④ 基础设施 | mod 本身是别人的地基 | 自身分析 + 依赖图：谁依赖它、谁自带重复副本、与谁冲突 |

无论哪一档，第 3 节的四个锚点都必须答完。看到“被大量 mod 声明依赖、自带公共库、位于转换/事件管线中”等信号时应升到第 ④ 档。

## 5. 阳性对照与自查纠错

任何“0 命中 / 全缺失”的扫描结论都必须先证明工具能在已知有效样例上命中，否则不能采信。

硬性规则：

1. 报告 0 命中前，先用阳性对照证明扫描器有效。
2. 判断文件为空前读真实字节数，不使用会四舍五入的列表输出。
3. 不假设 XML 属性顺序；必要时穷举声明形式或做两次独立匹配。
4. 工具犯错必须写进「怎么验的」，不能悄悄改掉结论。
5. 贴图、音频、程序集缺失结论必须说明本机素材是否完整，以及用什么方法交叉验证。

## 6. 提炼到知识库

记录的「可复用结论」是原料；[`docs/knowledge/`](../docs/knowledge/README.md) 中的 guides、reference、mechanics 是成品。

提炼只在你明确说“提炼”时执行，不自动触发，也不把未审核推断搬进知识页。提炼时：

1. 只选已经复核、脱离单个 mod 仍成立的结论。
2. 写入最合适的知识层，并把去向登记到 `record.json.distilled_to`；知识页底部的
   `## 来源记录` 段由 `tools/kb/sync_knowledge_sources.py --write` 生成，
   不要手工维护 ID 列表。
3. 如果结论与其他页面冲突，先修正冲突，不允许长期保留两套说法。
4. 修改建议仍留在记录中；没有明确授权，不因记录里存在建议就改动第三方 mod。

## 7. 元数据

| 字段 | 含义 |
|---|---|
| `schema_version` | 元数据版本；当前为 2 |
| `id` | 从此不再变化的稳定 ID |
| `package_id` | 分析对象的 packageId，可为空 |
| `display_name` | 可读名称 |
| `origin` | `owned` / `collected`，表示内容来源 |
| `authors` | 作者列表；作者证据放正文或 `author_evidence` |
| `author_evidence` | 可选，作者判断的证据列表 |
| `license` | 已核实授权；未声明时明确写“未声明”，不能留空 |
| `license_notes` | 可选，许可链、例外和再分发限制 |
| `source_url` | 可选，原始仓库或工坊页面 |
| `workshop_id` | 可选，Steam 工坊 ID |
| `retrieved_at` | 可选，`YYYY-MM-DD` 获取日期 |
| `source_dir` | 游戏 Mods 目录中的来源目录名 |
| `status` | `raw` / `analyzed` / `needs-recheck` / `superseded` / `retired` |
| `verification_tier` | `1`–`4`，对应上面四档核验 |
| `modifications` | 已实际执行的改动，不是建议 |
| `distilled_to` | 已提炼到的知识页相对路径列表 |
| `code_removed` | 是否已删除代码但保留记录 |

新记录可直接复制 [`tools/kb/templates/record/`](../tools/kb/templates/record/) 的
`record.json`；模板不放在 `records/` 下，避免被记录扫描器当成真实记录。
