# records — Mod 分析记录标准

> 开始分析任何 mod 前先读本页。记录保存调查过程、证据、反面发现和修改建议，不等同于 mod 代码样本，也不等同于提炼后的通用知识。

## 1. 两档记录

| 档 | `analysis_tier` | 用途 | 边界 |
|---|---|---|---|
| **初步分析** | `initial` | 快速判断这个 mod 大概做什么、值不值得继续、下一步查什么 | 不写可复用结论和修改建议；不能提炼进知识库 |
| **深度分析** | `deep` | 支撑修改、发布、兼容性/安全/许可判断，以及知识提炼 | 不能把未核验推断写成事实 |

- `analysis_tier` 是必填字段，只能是 `initial` 或 `deep`。
- 同一个 `records/<stable-id>/` 原地升级；不新建重复目录，也不把深度记录降级。
- 新 mod 默认先写初步分析。任务明确要求补丁、发布、基础设施分析，或已有高风险线索时，可以直接写深度分析。
- 修改/发布某个 mod、把结论提炼进知识库、或要下兼容性/安全/许可结论之前，必须有深度记录。
- 基础设施、被大量依赖、多版本/多程序集、证据互相冲突的 mod，建议深挖；单纯文件多、Def 多不构成强制。

## 2. 身份与目录

- 记录目录名来自 [`mods/registry.json`](../mods/registry.json) 的稳定 `id`，不使用旧编号或“源目录名必须一致”的规则。
- 记录可以只对应分析对象，不一定在 `mods/` 中有代码样本；这类条目在注册表中是 `code: null` + `record` 非空。
- 每份记录目录同时包含 `README.md` 与 `record.json`；`record.json` 是索引和校验读取的元数据来源。
- `package_id`、作者、授权和来源目录写进 `record.json`；正文补充当时的证据细节。
- 身份冻结后不随来源目录改名而变；需要重命名时在注册表登记 `aliases`，不迁移已有记录 ID。

## 3. 初步分析

### 3.1 骨架

```markdown
# <mod 名称> — 分析记录

## 身份卡

## 它是什么

## 初步核验

### 已核验

### 未核验

## 下一步
```

### 3.2 最低要求

- `身份卡` 至少记录：名称 / packageId / 作者 / 授权 / 来源 / 规模 / 类型 / 支持版本 / 外部依赖及安装状态。
- `它是什么` 只写这个 mod 自己的功能、关键文件和明显特征，不写评价。
- `### 已核验` 写实际看过的文件、来源和方法；能写清路径、命令或工具版本更好。
- `### 未核验` 写没看什么、哪些结论不能下、为什么。没有阳性对照时，否定性结论只能写“未核验”，不能写“缺失 / 不存在 / 0 命中”。
- `下一步` 写是否值得深挖、优先查什么。修改方向只能写成待验证问题，不能写成建议。
- 初步记录禁止 `## 可复用结论`、`## 修改建议` 和非空 `distilled_to`。
- 初步记录完成后，`status` 使用 `analyzed`。

模板：`tools/kb/templates/record/initial/`。

## 4. 深度分析

### 4.1 骨架

```markdown
# <mod 名称> — 分析记录

## 身份卡

## 它是什么

## 怎么验的

### 范围

### 方法

### 阳性对照

### 自查纠错

### 未核验

## 可复用结论

## 修改建议        ← 可选
```

- `### 范围` 写查了哪些版本、维度、文件和目录，哪些没查。
- `### 方法` 建议写可复现路径、命令、工具和版本；不是硬性标题，`## 怎么验的` 本身可以承担方法节。
- `### 阳性对照` 只在出现“0 命中 / 缺失 / 不存在”等否定结论时必须出现。
- `### 自查纠错` 只在分析过程中工具犯错或被纠正时必须出现。
- `### 未核验` 写仍未确认的边界、不能下结论的部分。
- 新写的深度记录应包含 `### 范围` 和 `### 未核验`；现有 28 份旧记录在下一次复核时补齐。
- `## 可复用结论` 的每条结论必须标 `[已确认]`、`[推断]` 或 `[未核验]`；旧记录在下一次复核时补标签。
- `## 修改建议` 只列待办，不把建议写成已执行的改动；没有就删掉整节。

模板：`tools/kb/templates/record/deep/`。

### 4.2 深度档最低证据

深度档至少要能回答“这个结论是怎么来的、别人怎么复查”：

- 身份、来源、作者和许可证据可追溯；作者证据写 `author_evidence`，许可链和例外写 `license_notes`。
- 方法和环境可复现：至少写清路径/命令/工具；涉及运行时结论时写游戏版本、mod 版本和运行条件。
- 多版本 mod 写版本矩阵：声明版本 × 实际版本目录 × 实际编译/加载条件。
- 依赖要区分 `modDependencies`、`loadAfter` 和代码/程序集引用，不能把 `loadAfter` 当成硬依赖。
- 静态分析不能冒充运行时验证；无法启动游戏验证的结论必须标 `[未核验]` 或写进 `### 未核验`。
- 外部资料给 URL 和访问日期；许可识别要读许可证正文，不能只看 README 徽章。
- 否定性结论必须有阳性对照；工具犯错必须写进 `### 自查纠错`。

### 4.3 方法指南

具体审计手法见 [`docs/knowledge/guides/mod-static-audit.md`](../docs/knowledge/guides/mod-static-audit.md)。
下表是**按 mod 规模选择手法**的指南，不是记录档位，也不写入 `record.json`：

| 手法档 | 触发条件 | 常用手法 |
|---|---|---|
| 极小 | 2–4 文件、纯 XML | 精读 + 交叉引用 + 贴图核实 |
| 中 | ~15 文件、单一机制 | 精读 + 逐文件 diff + IL 反射 |
| 大 | 30+ 文件 / 150+ Def | 脚本批扫 defName、ParentName、引用字段与 texPath，再精读关键片段 |
| 基础设施 | mod 本身是别人的地基 | 自身分析 + 依赖图：谁依赖它、谁自带重复副本、与谁冲突 |

同一个 mod 可以组合多种手法；看到“被大量 mod 声明依赖、自带公共库、位于转换/事件管线中”等信号时应增加依赖图分析。

## 5. 状态、提炼与升级

### 5.1 状态

`status` 与 `analysis_tier` 正交：档位表示投入深度，状态表示记录当前是否可信。

| `status` | 含义 |
|---|---|
| `analyzed` | 记录已完成（对初步档或深度档而言） |
| `needs-recheck` | 结论可能过期或证据有缺口，需要复核 |
| `superseded` | 已被另一份记录取代 |
| `retired` | 对象已退役或代码已移除，记录保留 |

- 不再使用 `raw`。记录一旦建目录，就应是完整的初步或深度记录。
- `needs-recheck` 阻止新的提炼，但已有 `distilled_to` 保留；门禁会提示复核对应知识页。
- `superseded` / `retired` 同样保留已有来源链，方便追溯。

### 5.2 提炼

记录的「可复用结论」是原料；[`docs/knowledge/`](../docs/knowledge/README.md) 中的 guides、reference、mechanics 是成品。

提炼只在你明确说“提炼”时执行，不自动触发，也不把未审核推断搬进知识页。提炼时：

1. 只选已经复核、脱离单个 mod 仍成立的结论。
2. 只有 `analysis_tier: deep` 且 `status: analyzed` 的记录可以写入 `distilled_to`。
3. 写入最合适的知识层，并把去向登记到 `record.json.distilled_to`；知识页底部的
   `## 来源记录` 段由 `tools/kb/sync_knowledge_sources.py --write` 生成，不要手工维护 ID 列表。
4. 如果结论与其他页面冲突，先修正冲突，不允许长期保留两套说法。
5. 修改建议仍留在记录中；没有明确授权，不因记录里存在建议就改动第三方 mod。

### 5.3 升级

- 初步 → 深度：同一 `records/<id>/`、同一稳定 ID，补深度骨架和证据，把 `analysis_tier` 改为 `deep`；旧版本由 Git 历史保留。
- 不新建 `-initial` / `-deep` 副本。
- 深度记录不降级；证据失效用 `status: needs-recheck` / `superseded` 表达。

### 5.4 复核触发

出现以下情况时，把记录标为 `needs-recheck`，不要静默改结论：

- mod 或游戏版本更新；
- 依赖或兼容性声明变化；
- 新的反面证据与现有结论冲突；
- 许可、作者或来源链需要重新确认；
- 原本标为 `[推断]` / `[未核验]` 的结论要升级为 `[已确认]`。

## 6. 元数据

| 字段 | 含义 |
|---|---|
| `schema_version` | 元数据版本；当前为 3 |
| `id` | 从此不再变化的稳定 ID |
| `package_id` | 分析对象的 packageId，可为空 |
| `display_name` | 可读名称 |
| `origin` | `owned` / `collected`，表示内容来源 |
| `authors` | 作者列表；作者证据放 `author_evidence` |
| `author_evidence` | 作者判断的证据列表 |
| `license` | 已核实授权；未声明时明确写“未声明”，不能留空 |
| `license_notes` | 许可链、例外和再分发限制 |
| `source_url` | 可选，原始仓库或工坊页面 |
| `workshop_id` | 可选，Steam 工坊 ID |
| `retrieved_at` | 可选，`YYYY-MM-DD` 获取日期 |
| `source_dir` | 游戏 Mods 目录中的实际来源目录名 |
| `status` | `analyzed` / `needs-recheck` / `superseded` / `retired` |
| `analysis_tier` | `initial` / `deep` |
| `modifications` | 已实际执行的改动，不是建议 |
| `distilled_to` | 已提炼到的知识页相对路径列表；仅深度且 `analyzed` 可用 |
| `code_removed` | 是否已删除代码但保留记录 |

`verification_tier` 已移除。原来的“四档核验”只保留为上面的方法指南，不再作为记录字段。
